Under the hood · plain english

How the pieces actually run

Worth understanding one honest constraint: there's no always-on server humming in the background here. Everything is arranged around that.

The appartifact page
A single web page you open — no install, works on your phone in a charity shop and on your laptop at home. This is Flip Check, growing into Scout.
The memorydb capability
Your finds, estimates and outcomes stored durably and synced across devices — the record the learning loop reads back from.
The judgementsample capability
Item identification and valuation run on Claude, paid from your own usage, triggered when you ask — not in a constant loop.
The scannerscheduled trigger
A task that wakes on a schedule, pulls fresh listings through the data adapter, values them, and updates your board — then sleeps. This is how "automatic" happens without a server.
The sourceswappable adapter
One clean seam where the listing data comes from. Sample data today; eBay Browse API or a paid feed slotted in behind it later, with no rebuild.
Straight talk · what could go wrong

Risks worth naming now

eBay may never grant live API access
Mitigated by the adapter: if Browse access doesn't come, a paid third-party feed drops into the same slot. The build never stalls on eBay's decision.
Final sold prices can't be captured automatically
The closed data. Phase 1 handles it the honest way — you confirm the price, the system learns from it. Not a blocker, just manual.
"Scan everything, everywhere" fights your only edge
Valuing a category you don't know is guessing. The niche-first design is the guardrail; Phase 3 widens only on proven accuracy.
Browser-bot scraping as a shortcut
Tempting because it sidesteps the API wall — but it's fragile, blockable and against ToS. Kept out of the plan on purpose; APIs first, always.
